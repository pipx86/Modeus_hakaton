# Событие run.completed

## Формат запроса

Обработчик отправляет HTTP POST с `Content-Type: application/json`. Тело содержит JSON с полями `event` (`run.completed`), `run_id`, `profession`, `finished_at` (может быть null). Заголовок `X-Webhook-Signature` содержит HMAC-SHA256 точных байтов тела, закодированный строчными шестнадцатеричными символами без префикса. Секрет — значение `WEBHOOK_SECRET` в UTF-8.

Получатель должен вычислить HMAC по полученным исходным байтам, не преобразуя JSON, и сравнить подпись безопасным сравнением. Секрет получателя и отправителя должен совпадать и передаваться через настройки окружения, а не храниться в репозитории. При неверной подписи запрос следует отклонить. Это выбранный формат проекта; реальный workflow n8n ещё нужно настроить и проверить.

## Обработчик очереди

После применения миграций можно запустить `go run ./cmd/webhook-worker`. Ему нужны переменные окружения `DATABASE_URL` (адрес PostgreSQL), `WEBHOOK_URL` (адрес получателя) и `WEBHOOK_SECRET` (общий секрет). Процесс нужно запускать отдельно и держать работающим: сам по себе триггер базы не запускает процесс.

Когда сохранённый в PostgreSQL статус исследования меняется на `done`, триггер создаёт событие в `agent_messages`. Обработчик ищет готовые сообщения `run.completed` и отправляет их с подписью. При успешном ответе 2xx он отмечает событие как отправленное; при ошибке отмечает его как failed и повторяет попытку через минуту.

Несколько обработчиков не возьмут одну запись одновременно, но при остановке между получением ответа и записью результата возможна повторная доставка. Получатель должен исключать дубликаты по паре `event` и `run_id`. Во время отправки обработчик удерживает блокировку строки; HTTP-клиент ограничивает время ожидания.

Для интеграционного теста нужна отдельная тестовая PostgreSQL с применёнными миграциями: установите `OUTBOX_TEST_DATABASE_URL` и выполните `go test ./...`. Без этой переменной тест очереди пропускается.
