# sqlc и store

`sqlc` v1.30.0 генерирует Go-код из SQL-запросов в `db/queries`, используя Goose-миграции как описание схемы. После изменения SQL выполните `sqlc generate` из корня проекта. Для актуальной схемы применяются все основные миграции из каталога `migrations/`; необязательный векторный пакет имеет отдельный порядок установки.

`store.New(pool)` принимает пул pgx. Методы сгенерированных запросов доступны через store; ошибки отсутствующей записи возвращаются драйвером. Методы удаления возвращают число удалённых строк.

`SaveTree(ctx, runID, root)` сохраняет новое дерево и его подтверждения одной транзакцией. Узлы передаются вложенно, начиная с роли; каждый узел требует хотя бы одно подтверждение. Уровни следуют порядку роль → функция → задача → действие. Узлам и подтверждениям нужно заранее назначить UUID; ссылки на источники должны существовать. Повторное создание для исследования с корнем отклоняется. При ошибке сохраняется прежнее состояние базы. Для изменения существующего дерева используйте CRUD; полноценная атомарная замена дерева здесь не реализована.

Интеграционный тест требует отдельную тестовую PostgreSQL с применёнными миграциями. Укажите `STORE_TEST_DATABASE_URL`, затем запустите `go test ./internal/store/...`. Без переменной интеграционный тест пропускается. Не используйте рабочую базу для тестов.

`RunStatusStore` предоставляет метод `Save` для записи `runs.status` из оркестратора. Исследование должно уже существовать в PostgreSQL и иметь UUID. В схеме уже есть `stage`, но этот адаптер его не обновляет: в бэкенде для состояния оркестратора предусмотрен `api.PGStore`, сохраняющий этап вместе со статусом. Сам по себе адаптер не подключает оркестратор к базе. Для операций нужен положительный `Timeout`.

## Снимки дерева

`SaveSnapshot(ctx, runID)` по явному запросу сохраняет текущее дерево исследования и возвращает запись снимка. Версии назначаются отдельно для каждого исследования; параллельные запросы получают разные номера. Создание снимка без корневого узла отклоняется. Получить снимок или список версий можно методами `GetSnapshot` и `ListSnapshotsByRun`.

В `tree` хранится JSON версии формата `schema_version: 1`: корень и список узлов со связями через `parent_id`. У каждого узла хранится список подтверждений: идентификатор, необязательный `ref_id` фрагмента, цитата, признак одобрения, а также идентификатор, тип, название и ссылка источника. Полный текст и исходные данные источника не копируются. Старый снимок не меняется после редактирования или удаления источника, узла либо подтверждения. При удалении исследования связанные снимки удаляются — как предусмотрено существующей схемой. Снимки не заменяют резервное копирование базы.

В ветке бэкенда доступны HTTP-маршруты создания и чтения снимков. Снимок создаётся явно по запросу, автоматическое создание не включено.

## Общие источники

`run_sources` связывает один источник с несколькими исследованиями. `LinkSourceToRun` добавляет связь без дубля; `ListSourcesByRun` читает связи из новой таблицы. Прежнее поле `sources.run_id` временно сохранено для совместимости: существующие связи переносит миграция, новые записи старого кода добавляются триггером. Изменение или очистка этого поля не удаляет существующие связи. При наличии подтверждений удаление источника запрещено; прежде чем удалить источник, нужно отдельно решить вопрос с его подтверждениями. Откат миграции удаляет дополнительные связи, поэтому перед откатом нужна резервная копия.

## Проверка качества дерева

`go run ./cmd/data-audit` проверяет данные во всей базе из `DATABASE_URL` и создаёт JSON-отчёт в `data/reports/` или папке `DATA_REPORTS_DIR`. Отчёт содержит идентификаторы и коды проблем без цитат. Пустое название, сирота, дубли у родителя, отсутствие evidence и цикл считаются P0. Код самой программы: 0 — критичных проблем нет, 1 — есть P0, 2 — ошибка запуска. Неизвестный код также считается P0. `make check-data` запускает программу через GNU make; при ошибке make может вернуть свой ненулевой код. Сам отчёт только обнаруживает ошибки. Дополнительно отложенные ограничения PostgreSQL не позволяют зафиксировать дерево, нарушающее предусмотренные правила. Файл CI `.github/workflows/db-checks.yml` подготовлен; его выполнение на GitHub ещё не проверено.

Один источник автоматически связывается с исследованием при добавлении подтверждения к его узлу. Прямая попытка удалить используемую связь блокируется базой. Это не заменяет полный валидатор дерева.

Перед `SaveTree` выполняется `ValidateTree`: у узла проверяются идентификатор, название и наличие подтверждения, у одного родителя — повторы названий, у дерева — повторы ID, циклы и глубина. Возвращается `TreeValidationError` с кодом и данными узла. Вложенный формат задаёт родителей структурой. Отдельные SQL CRUD-операции не вызывают эту проверку Go, но PostgreSQL дополнительно проверяет итоговое дерево при фиксации транзакции. Подключение валидатора и сопоставление ошибок к API остаются отдельной задачей.

## Внешние идентификаторы источников

`provider` задаёт поставщика строчными буквами, например `hh`; `external_id` — ID материала у него. Сочетание поставщика, типа и внешнего ID уникально, когда оба поля заполнены. Старые и ручные источники могут иметь неизвестного поставщика; автоматически считать их уже импортированными нельзя. `UpsertExternalSource` добавляет материал или обновляет существующий без создания дубликата; для неё поставщик и внешний ID обязательны. Этот запрос сам по себе не загружает данные с hh.ru и не сообщает отдельно число добавленных, обновлённых и пропущенных записей. Загрузчик подготовлен в отдельной ветке бэкенда, но реальный API ещё не проверен. При откате миграции информация о поставщике будет потеряна.

## Демонстрационные данные

`make seed` (или `go run ./cmd/demo-fixture`) по `DATABASE_URL` создаёт синтетическое исследование аналитика данных: 1 роль, 3 функции, 12 задач и 36 действий, у каждого узла есть цитата. Источник и цитаты явно помечены как вымышленные. Дерево проверяется валидатором и создаётся одной транзакцией. Повторная команда проверяет набор и не создаёт дубли; если существующие данные изменились, она завершится ошибкой и ничего не перезапишет. Для тестов нужна выделенная БД.

## Целостность дерева в PostgreSQL

Миграция `20261109000005_tree_consistency.sql` добавляет отложенные проверки: дерево с некорректным корнем, родителем, уровнем, названием, дубликатом у родителя или узлом без подтверждения не может быть зафиксировано. Узел и его подтверждения можно добавить отдельными операциями внутри одной транзакции: сначала создаётся узел, затем подтверждение, а к моменту фиксации всё дерево должно быть корректным. Удаление последнего подтверждения у существующего узла запрещено: сначала нужно добавить замену либо удалить узел. Изменения одного исследования сериализуются, чтобы конкурентные операции не обошли правило. В отдельной ветке бэкенда добавлена запись дерева через API с ответом 422 и сопоставлением ошибок PostgreSQL; проверено на отдельной тестовой базе.

Перед применением миграции к базе с данными необходимо запустить проверку качества и устранить проблемы: миграция проверит старые деревья и откажется применяться, если они некорректны. На тестовой базе это поведение проверено; данные автоматически не удаляются и не исправляются.
