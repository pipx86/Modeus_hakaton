# 07. Повтор интервью без модели: `cmd/interview-replay`

**Статус:** готово к использованию на стенде. Карточка плана MVP — проверка
жизненного цикла исследования после сбоя провайдера.

## 1. Зачем

Провайдер LLM может быть недоступен: ключ истёк, кончилась квота, провайдер
вернул 5xx. В этом случае интервью завершается статусом `failed`, но ответы и
история уже сохранены. Это не тупик: анализ можно запустить заново кнопкой
**«Повторить анализ»** на странице исследования или запросом
`POST /api/v1/runs/{id}/retry`.

`cmd/interview-replay` нужен, чтобы:

- прогнать один и тот же сценарий интервью на живом backend без ручного чата;
- убедиться, что API, чат и финализация работают после правок;
- воспроизвести падение провайдера и проверить, что интерфейс предлагает
  повтор, а не показывает тупик;
- получить машинный отчёт (`-json`) для логов и сравнения прогонов.

Сценарий встроен в бинарь (`scenario.json` + `go:embed`), поэтому не зависит от
модели и от сети: вопросы и ответы всегда одинаковые. Это 10 реплик — 5
вопросов интервьюера и 5 ответов «Аналитика данных»; сценарий покрывает все
четыре уровня дерева (`role → function → task → action`) и даёт материал для
8–12 узлов. Первый вопрос начинается с приветствия интервьюера.

## 2. Что делает команда

1. Создаёт chat-исследование (`POST /runs` с `type: chat`).
2. Поллит `GET /runs/{id}/messages`, пока последнее сообщение не станет
   вопросом агента. Если прогон уже завершился, ожидание прекращается.
3. Отправляет следующий ответ (`POST /runs/{id}/messages`). На
   `CHAT_CONFLICT` («интервьюер готовит вопрос») отправка повторяется.
4. После всех ответов поллит `GET /runs/{id}`, пока статус не станет `done`,
   `degraded` или `failed`.
5. Печатает `run_id`, статус, число узлов (`GET /runs/{id}/tree`), число
   обоснований (сумма `evidence` по узлам) и число конфликтов
   (`GET /runs/{id}/conflicts`).

Число конфликтов доступно только роли `admin`: для остальных эндпоинт отвечает
403, и CLI печатает `конфликтов: н/д`, не считая это ошибкой прогона.

## 3. Как запускать

### 3.1. Подготовка стенда

Нужен запущенный backend, например:

```bash
go run ./cmd/server
curl -sS http://127.0.0.1:8080/api/v1/health
```

Для `cmd/server` нужна PostgreSQL и применённые миграции — см.
[05-pilot-runbook.md](05-pilot-runbook.md), раздел 2.

Токен выпускается локально или берётся из логина. Токен не храните в файлах
репозитория:

```bash
# локальный JWT (роль admin нужна для счётчика конфликтов)
go run ./cmd/local-token -role admin
```

```powershell
$env:MODEUS_TOKEN = "<admin-token>"
```

```bash
export MODEUS_TOKEN="<admin-token>"
```

### 3.2. Проверка без сети

```bash
go run ./cmd/interview-replay -dry-run
```

Команда печатает сценарий (уровни, вопросы, ответы), не делает ни одного
запроса и выходит с кодом `0`. Токен в этом режиме не нужен. То же в машинном
виде:

```bash
go run ./cmd/interview-replay -dry-run -json
```

### 3.3. Прогон с ключом LLM

Заполните в `.env` (или в окружении) `LLM_API_KEY`, `LLM_BASE_URL` и модели
агентов, затем перезапустите backend. Полный список переменных —
[`.env.example`](../../.env.example), раздел «LLM provider».

```bash
go run ./cmd/interview-replay \
  -base-url http://127.0.0.1:8080 \
  -profession "Аналитик данных" \
  -timeout 10m
```

Ожидаемо: статус `done`, ненулевые узлы и обоснования, код выхода `0`.
Если модель отвечает медленно, увеличьте `-timeout` (по умолчанию `10m`).

### 3.4. Прогон без ключа LLM

Без `LLM_API_KEY` backend поднимается, но интервьюер работает в
детерминированном fallback-режиме, а построение дерева требует настроенного
LLM-аналитика. Поэтому прогон ожидаемо завершится `failed`:

```bash
go run ./cmd/interview-replay -base-url http://127.0.0.1:8080
```

Это полезная проверка «плохого» сценария: команда должна выйти с кодом `2`,
напечатать подсказку про **«Повторить анализ»** и `POST /runs/{id}/retry`, а
интерфейс исследования — показать блок «Интервью не завершилось» с кнопкой
повтора. Тот же результат бывает и с ключом, если провайдер временно недоступен
(429, 5xx, таймаут).

### 3.5. Флаги

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `-base-url` | `http://127.0.0.1:8080` | Адрес backend. `-base-url` — только схема и хост, без `/api/v1` |
| `-profession` | `Аналитик данных` | Профессия создаваемого исследования |
| `-token` | пусто | Bearer-токен; если пуст, берётся `MODEUS_TOKEN` |
| `-dry-run` | `false` | Напечатать сценарий и выйти `0` без сети |
| `-answers` | все (`-1`) | Сколько ответов отправить; `0` — не отправлять ответы |
| `-timeout` | `10m` | Сколько ждать финального статуса `done`/`failed` |
| `-json` | `false` | Машинный JSON вместо текста |

## 4. Коды выхода

| Код | Значение | Что делать |
|---:|---|---|
| `0` | Прогон завершён: `done` или `degraded` (результат неполный, но дерево есть) | Проверить узлы и обоснования, при необходимости — дерево в интерфейсе |
| `2` | Прогон `failed`, ошибка сети/API, таймаут ожидания или неверные флаги | При `failed` — нажать «Повторить анализ» или повторить POST retry; при сетевой ошибке — проверить backend и токен |
| `3` | Нет токена (`-token` не задан и `MODEUS_TOKEN` пуст) | Выпустить JWT и задать `MODEUS_TOKEN`; для `-dry-run` токен не нужен |

`failed` — не окончательный провал сценария: это штатный результат, который
проверяет ветку восстановления. Поэтому CLI печатает явную подсказку, а не
только код `2`.

## 5. Если прогон упал

CLI печатает:

```text
Интервью не завершилось: анализ упал, но ответы и история сохранены.
Подсказка: нажмите «Повторить анализ» или выполните POST /runs/<run_id>/retry.
```

Дальше два равноправных пути:

1. Открыть исследование в интерфейсе, нажать **«Повторить анализ»** на блоке
   «Интервью не завершилось». Кнопка шлёт `POST /api/v1/runs/{id}/retry`,
   показывает тост и возобновляет поллинг статуса. Если дерево уже построено,
   придёт сообщение «Дерево уже построено, обновите страницу»; если анализ уже
   идёт — «Анализ уже выполняется».
2. Выполнить запрос вручную:

   ```bash
   curl -sS -X POST "http://127.0.0.1:8080/api/v1/runs/<run_id>/retry" \
     -H "Authorization: Bearer $MODEUS_TOKEN"
   ```

   Backend отвечает `202` (повтор запущен), `409` (повтор невозможен: дерево уже
   есть или анализ уже выполняется) или `404` (run не найден). После `202`
   статус снова становится `pending`/`running`; тот же прогон можно наблюдать
   в интерфейсе или повторно проверить CLI.

Повтор не создаёт новое интервью: ответы и история остаются у исходного
`run_id`, поэтому заново проходить чат не нужно.

## 6. Ограничения

- CLI не заменяет ручное интервью и не проверяет качество ответов: сценарий
  фиксированный, ответы написаны заранее.
- Счётчик конфликтов недоступен без роли `admin`; в этом случае выводится
  `н/д`. Счётчики узлов и обоснований читаются из `GET /tree`, поэтому при
  недоступном дереве они будут нулевыми с предупреждением.
- Команда ждёт финализацию только до `-timeout`; при таймауте `run_id`
  остаётся в выводе, но итоговый статус нужно проверить вручную.
- Сессия чата живёт на backend: `failed`-прогон сохраняет историю, но новый
  процесс backend без настроенного хранилища сессий может её не восстановить.

## 7. Проверка

```bash
go build ./cmd/interview-replay
go vet ./cmd/interview-replay
go test ./cmd/interview-replay/
```

Тесты не ходят в модель и не требуют базы: успешный прогон и прогон с `failed`
проверяются на `httptest`-сервере, `-dry-run` — без сети.
