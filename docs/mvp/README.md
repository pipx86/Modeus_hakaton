# MVP: методические карточки

Рабочая папка команды в ветке `feature/mvp-foundation`. Здесь лежат три методических артефакта, которые фиксируют рамку пилота: что получает методист, на какой профессии и программе проверяем систему и какими уровнями описываем деятельность. Это не техническая спецификация и не замена плану MVP.

## Зачем эта папка

Без трёх решений пилот нельзя корректно принять:

1. **Что считается результатом.** Дерево без обоснований и дерево с проверенными обоснованиями — разные результаты; методист должен понимать, что он проверяет и что может исправить.
2. **На чём проверяем.** Профессия, программа и респондент выбираются по критериям, а не по удобству; иначе пилот не проверит универсальность и сопоставимость.
3. **Как называем уровни.** Пока «функция», «задача» и «действие» понимаются по-разному, два методиста получат разные деревья из одного материала.

## Общие границы, на которые опираются документы

| Статус | Что это значит в этой папке |
|---|---|
| **Поддержано** | Работает в текущей реализации: дерево `role → function → task → action`; обязательное обоснование у каждого узла; статусы обоснований `pending / approved / rejected`; снимки и дифф; правка названия и описания; справочники программ. |
| **Не реализовано** | Комментарий к узлу; статус проверки узла; сопоставление деятельности с программой; переклассификация и перенос узла; у узла нет собственного статуса `approved`. |
| **В работе** | Поддержка нескольких респондентов в одном исследовании. До приёмки не закладываем её в обязательный сценарий пилота. |
| **Требует подтверждения** | Методическое решение: формулировки, критерии выбора, пороги и объём сопоставления. Это не описание уже работающей функции. |

Три технических ограничения, важных для всех карточек:

- узел без обоснования не сохраняется, но **наличие обоснования не равно его проверке**: дерево может существовать с обоснованиями в статусе `pending`, а узел — даже с одними `rejected`;
- промпты агентов сейчас разрешают только три IT-роли: аналитик данных, DevOps-инженер, backend-разработчик. Пилот вне этого списка требует снятия технического долга до запуска;
- сопоставление с образовательной программой — направление D плана; в текущем коде его нет, поэтому в карточке 1 расширенный результат описан как целевой, а в карточке 2 выбирается только его объём для MVP.

## Порядок работы

1. Подтвердить карточку 1: что методист получает и какие действия считаются обязательными.
2. Подтвердить карточку 3: определения и правила классификации, затем провести калибровку на двух людях.
3. Заполнить карточку 2: выбрать вариант, проверить источники и данные программы, зафиксировать решение.
4. Только после этого запускать пилот: у него появляются измеримые критерии результата и выбранный объект.

Карточки 1 и 3 можно согласовывать параллельно; карточка 2 зависит от обеих.

## Критерий готовности папки

Папка готова к пилоту, когда:

- все три документа переведены из статуса «черновик» в «подтверждено» с датой и ответственным;
- в карточке 2 заполнен decision record, проверены источники и данные программы, решение подписано владельцем продукта и методистом;
- в карточке 1 согласован пример результата и перечень действий, которые методист выполняет без разработчика;
- в карточке 3 проведена калибровка: два человека независимо классифицировали контрольный набор и совпали по уровням.

До выполнения этих пунктов результаты пилота считаются исследовательскими, а не основанием для актуализации программы.
