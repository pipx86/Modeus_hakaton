# Архитектура пайплайна агентов

Ориентир: `Архитектура (2).docx` — слоистый pipeline с оркестратором,
стадиями, прогрессом, сохранением результатов и мониторингом.

Важное отличие: у нас **только профессиональные роли**. Руководитель,
методист, оператор и другие бизнес-роли в текущий этап не входят.

## Принцип

Пайплайн — последовательность стадий. Каждая стадия:

1. получает вход;
2. выполняет одну задачу;
3. сохраняет промежуточный или итоговый результат;
4. обновляет стадию, статус и прогресс;
5. отправляет SSE-событие;
6. при ошибке ретраится или переводит run в degraded/failed.

Оркестратор не содержит бизнес-логики. Он только управляет порядком стадий,
повторами, таймаутами и сохранением состояния.

## Стадии

| Стадия | Что делает | Вход | Выход | Прогресс |
|---|---|---|---|---|
| Interview | Чат с носителем профессиональной роли | профессия, run | стенограмма, ответы, сообщения | 0–20% |
| Analysis | Аналитик извлекает функции, задачи и действия | стенограмма | сущности с evidence | 20–40% |
| Synthesis | Синтезатор собирает дерево и конфликты | сущности интервью, источники | дерево, конфликты | 40–60% |
| Review | Проверка и сохранение результата | дерево | nodes, evidence, snapshot | 60–80% |
| Done | Финальный статус | run | done/degraded | 100% |

Стадии соответствуют существующим `domain.Stage`:
`interview`, `analysis`, `synthesis`, `review`, `done`.

## Оркестратор

Интерфейс шага:

```go
type Step interface {
    Name() Stage
    Execute(ctx context.Context, run *Run) error
}
```

Для шагов, которым нужны данные из БД, используется `DataStep`.

Оркестратор:

- запускает шаги по порядку;
- пропускает уже пройденные стадии при resume;
- повторяет шаг при retryable-ошибке;
- соблюдает timeout;
- сохраняет stage/status после каждого шага;
- публикует событие `stage_change`;
- переводит run в `done`, `degraded` или `failed`.

## Два режима

### Chat

1. Создаётся run с `type=chat`.
2. `InterviewStage` запускает чат и ждёт ответы.
3. После последнего ответа стенограмма кладётся в `run.Data`.
4. Оркестратор продолжает с `analysis`.
5. Далее synthesis, review, done.

### Batch

1. Создаётся run с `type=batch`.
2. `InterviewStep` — заглушка.
3. Analysis и synthesis работают по вакансиям.
4. Review сохраняет предварительное дерево.
5. Run завершается.

## Входы и выходы

### Interview

- вход: `run_id`, профессия, respondent;
- выход: `InterviewSession`, transcript;
- события: `agent_thinking`, `agent_message`, `run_status`.

### Analysis

- вход: transcript, profession;
- выход: `AnalystOutput` (entities + evidence);
- проверки: evidence обязателен, цитата дословная, JSON по схеме.

### Synthesis

- вход: interview nodes, sources;
- выход: `tree`, `conflicts`, `messages`;
- правила: приоритет интервью > стандарт > вакансия, узел без evidence запрещён.

### Review

- вход: tree;
- выход: `nodes`, `evidence`, `snapshots`;
- проверки: иерархия, корень, циклы, дубли, evidence.

## Сохранение

Минимальный набор таблиц:

- `runs` — run, stage, status, type, degraded_reason;
- `run_sse_events` — история событий;
- `llm_requests`, `llm_responses`, `llm_usage` — аудит LLM;
- `prompt_versions`, `prompt_activations` — версии промптов;
- `nodes`, `evidence`, `snapshots` — результат;
- `agent_messages` — исходящие события, `dedup_key`.

## Мониторинг

- длительность каждой стадии;
- количество ошибок по стадии;
- токены и стоимость по агенту;
- fallback/degraded;
- прогресс run;
- SSE-события.

Метрики: Prometheus. Дашборды: Grafana. Логи: structured JSON с `run_id`,
`agent`, `stage`. Трассировка: OTel-спаны на стадию и LLM-вызов.
